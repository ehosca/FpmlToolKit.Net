# Contributing

Thank you for being here! Whether it's a bug report, a clearer sentence in the docs, a new example or a whole new FpML
version, your help makes FpmlToolKit.Net better for everyone who works with FpML in .NET. Small contributions are
just as welcome as big ones.

For a security problem, please follow [SECURITY.md](SECURITY.md) instead of opening a public issue.

## Get set up in three commands

Install the .NET SDK version in [`global.json`](global.json) (or any later feature band of .NET 10), then:

    dotnet tool restore
    dotnet build FpmlToolKit.slnx
    dotnet test FpmlToolKit.slnx

The first build generates C# from every FpML schema set, so give it a few minutes and grab a coffee. After that, builds
only regenerate the projects whose schemas or generation settings changed, and they're quick. On Windows the tests
also run on .NET Framework 4.8.

## Find your way around

| Path | What's there |
|---|---|
| `fpml-*/` | One project per FpML version and view. `xsd/` holds FpML's official schemas plus our `namespaceconfig.xml`. |
| `build/` | The shared MSBuild logic that generates C# with LinqToXsdCore and embeds the schemas (`FpmlSchema`). |
| `packages/` | One NuGet package project per FpML version, generated by `scripts/add-schema-version.cs`. |
| `scripts/` | `add-schema-version.cs` (add or update an FpML version) and `official-files.cs` (record and verify schema provenance). |
| `tests/FpmlToolKit.Tests/` | The test suite. `Examples/` are FpML's official example documents; `Samples/` are our own. |

## Reporting a bug

The most helpful reports include the package and version, your app's target framework, and a small FpML document or
code snippet that shows the problem. Not sure whether it's in the schema (FpML), the generated code (LinqToXsdCore) or
this repository? Report it here anyway and we'll work it out together.

## Ground rules

A few rules keep the project reliable:

- **Generated code is never committed or edited.** It lives in each project's `obj/` folder. To change it, change the
  generation (`build/LinqToXsd.targets`, `build/FpmlSchema.cs.template`, a project's `xsd/namespaceconfig.xml`) or fix
  the generator upstream in [LinqToXsdCore](https://github.com/mamift/LinqToXsdCore).
- **Official FpML files are never edited.** The schemas in `fpml-*/xsd/` and the examples in
  `tests/FpmlToolKit.Tests/Examples/` are byte-for-byte copies of FpML's downloads, listed with their SHA-256 in
  `official-files.txt`, and the tests fail if one changes. Your own test documents go in `tests/FpmlToolKit.Tests/Samples/`.
- **New FpML versions and builds** come in through the scripts; [MAINTAINING.md](MAINTAINING.md) walks you through it.
- **Generator and runtime versions move together.** The LinqToXsdCore version in `dotnet-tools.json` must equal
  `XObjectsCoreVersion` in `Directory.Build.props`.
- **Keep .NET Framework working.** Library code (including `build/FpmlSchema.cs.template`) must compile for
  `netstandard2.0`, and test code for `net48`.
- **Tests come with changes.** Add or update tests in `tests/FpmlToolKit.Tests` for behaviour you change, and keep the
  build free of warnings. If you touch a README example, update `ReadmeExampleTests` to match.

## Pull requests

- All changes go through pull requests against `main`, and they're merged with a merge commit.
- Keep each pull request to one change, and say what it changes and why.
- CI needs to be green: the `build` job (Linux: build, test on `net10.0`, pack) and the `windows` job (tests on
  .NET Framework 4.8). Changes to schemas, `dotnet-tools.json` or `build/LinqToXsd.targets` regenerate the affected
  projects in CI, which can take up to about 40 minutes.
- Add a line under **Unreleased** in [CHANGELOG.md](CHANGELOG.md) for anything users will notice.
